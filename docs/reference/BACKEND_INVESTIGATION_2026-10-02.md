## Q1 — Team rankings: absent page vs parse failure

**Observed behavior.** `parse_meet._team_rankings` catches every exception and returns `None` (`backend/parse_meet.py:63-84`). It also returns `None` when the parser returns a dict without `men` or `women` rows. `main()` then passes `None` to `_score_athletes` (`backend/parse_meet.py:102-107`); `_score_athletes` calls `calculate_points(raw_athletes)` without a meet boundary when `scored_event_number_max is None` (`backend/parse_meet.py:51-60`). The scorer documents `scoredEventNumberMax: None` as no published boundary, so all events remain eligible (`backend/point_calculator.py:239-241`). Thus a missing rankings page and a broken detected rankings page are indistinguishable today; both allow parsing to continue without the event-through cutoff.

**Run evidence.** Command: `python backend/parse_meet.py tests/fixtures/nsisc_psych_sheet.pdf`, with stdout redirected by PowerShell. Decoding that redirection as UTF-16 produced JSON with 428 athlete rows and `officialTeamScores: null`; parse completed successfully. `tests/fixtures/nsisc_psych_sheet.pdf` is the only PDF fixture found under the repository's test fixtures. This fixture therefore demonstrates that a PDF without a rankings summary can succeed today.

**Narrower rule.** Scan the same final pages for the explicit `Team Rankings - Through Event N` marker before attempting extraction. If absent, return `None` as now. If present, propagate extractor exceptions and reject an empty/unusable score block; the parser currently extracts the marker at `backend/team_rankings_parser.py:69` and scans the last pages at `:112-128`. The current fixture has no detected rankings (`officialTeamScores: null`) and succeeds, so the proposed marker-gated failure does not change that case. A detected-but-malformed rankings PDF was not present in the available fixture corpus; the exception behavior follows directly from the current catch-all at `parse_meet.py:82-83`.

## Q2 — Python parser output for rank, calculated points, and gender

`pdf_parser` initializes row rank as `None`, reads a leading place token as a string when present, and stores the current parsed gender (`backend/pdf_parser.py:354-372, 480-505`; relay equivalents at `:1051-1055, :1126-1140`). `point_calculator.calculate_points` subsequently adds `calculated_points` to meet rows (`backend/point_calculator.py:1044-1082`, plus scoring assignments at `:1142`, `:1279`, and related branches). Psych parsing normalizes rows and sets seed time and round, but does not calculate points (`backend/psych_parser.py:13-37`).

| Row type | Python `rank` | Python `calculated_points` | Python `gender` | Evidence / consequence |
| --- | --- | --- | --- | --- |
| Placed result | Place parsed from the PDF as a string such as `"1"`; scorer can later alter/retain its own rank representation. | Meet scoring adds numeric values (usually float, including `0.0`) or `"N/A"` in specific non-scoring paths. | Parsed heading value, e.g. `"Men"` or `"Women"`. | Fixture run emitted 428 rows, with `rank` either a place string or `None` (2 rows had `None`), genders `Men`/`Women`, and `calculated_points` values of Python `float`; its rows were all `Finals`. See parser/scorer locations above. |
| DQ / DNS / DFS result | Usually `None` when the PDF's status token has no place; it may remain a string place if the source prints one. | Scorer assigns numeric zero for non-scoring status rows; its non-scoring regex includes DQ/DFS/NS/NP (`backend/point_calculator.py:414-437`, assignments e.g. `:497-519`). | Same parsed event heading. | `None` is not convertible into a genuine placing. The only fixture had no DQ/DFS/NS status rows, so exact raw values for those row types are established by code paths, not a fixture sample. |
| Timed-final result | The parser leaves rank `None` when the timed-final line has no leading place (`backend/pdf_parser.py:354-372`; timed-final split at `:394-445`). If a place is printed, it is a string. | Numeric float or `"N/A"` after meet scorer runs; unplaced results receive zero. | Parsed heading value. | In timed-final branch, place is optional; its absence does not mean malformed input. |
| Psych seed row | Optional parsed place as string or `None`; seed entries need not have a place. | **Absent**: `psych_parser` returns normalized source rows without calling the points scorer (`backend/psych_parser.py:13-37`); TypeScript `mapPsychRows` independently sets its product-facing points to `0` (`parsingPipeline.ts:131-151`). | Parsed heading value. | Rejecting missing `calculated_points` globally would break psych rows if that mapper were changed to require the Python field. |

**Mapping recommendation.** Do not reject missing rank: rank `0` is expressly “not placed yet” (`packages/core/src/lib/utils.ts:2407`), and raw parser rank can be `None`. For meet rows passed through `mapAthleteRows`, missing `calculated_points` can be rejected because that path runs the scorer first and the scorer writes the field; do not apply that requirement to psych seed rows. Missing/unknown gender should be rejected at the bridge rather than defaulted to Men: parser headings supply the gender for recognized event rows, and current bridge maps every non-`Women` value to Men (`apps/shell/lib/routes/parsingPipeline.ts:97-115, 131-147`). This would surface previously accepted malformed/undetermined-gender rows and may cause those imports to fail, which is the intended protection against silently assigning them to the wrong gender.

## Q3 — Scoring config at parse time and fresh checkout

`parseMeetUnified` launches Python with `OMNI_DATA_DIR` set from the route's data directory (`apps/shell/lib/routes/parsingPipeline.ts:34-55, 225-234`). `parse_meet` calls the scorer with raw rows and, optionally, only the event-through boundary; it does not pass TypeScript workspace scoring settings (`backend/parse_meet.py:51-60, 102-107`). `_resolve_scoring_settings` looks for `$OMNI_DATA_DIR/scoring_settings.json`, then repo `data/scoring_settings.json`, repo-root `scoring_settings.json`, and current-directory `scoring_settings.json` (`backend/point_calculator.py:150-208`). If none exists, `cfg.setdefault('scoringPoints', DEFAULT_NCAA_D2_SCORING)` applies the D2 values `[20,17,16,15,14,13,12,11,9,7,6,5,4,3,2,1]` (`backend/point_calculator.py:13, 216`).

The report and session-state audit found no `data/scoring_settings.json`; `data/scoring_presets/nsisc.json` is a separate preset and is not one of the lookup paths. `scoring_settings.json` is not present in this checkout's `data` directory. Therefore a fresh checkout without an external settings file reaches the D2 default on the product's unified PDF parse path. This is a real silent fallback, although the TypeScript `calculatePoints` path uses app/workspace settings separately (vault invariant: `utils.ts` owns product scoring).

**Minimal safe change.** Emit a conspicuous Python `stderr` warning when the config search finds nothing and the D2 scoring default is applied. This preserves the current row output and avoids changing the parser JSON contract or breaking fresh-checkout imports; it does not prevent incorrect point values. A hard error would break PDF parsing in fresh checkouts and any deployment whose settings are workspace-held rather than written to this legacy Python config path.

## Q5 — Gigi Gotaas DFS row and the NSISC entry cap

Workspace `Blank Workspace 1` contains Gigi Gotaas, UWF, Event 34 100 Free, `Preliminaries`, `time: "DFS"`, `rank: 0`, `points: 0` at `data/meets.json:58416-58433`. The corresponding archived SwimCloud Event 34 result shows Gotaas with `NS`, rather than a numeric placing (embedded HTML in capture file `data/swimcloud-captures/pages/https_...event_34...json`). Hy-Tek defines DFS as “Declared False Start”; the [Hy-Tek Swim Meet Manager 8.0 Quick Reference Guide](https://williamli9300.github.io/swimOfficialsToolkit/HyTekQuickReferenceGuide/HyTekQuickReferenceGuide.html) explains that DFS is distinct from initiating a start before the signal. Thus DFS is a non-scoring status, consistent with zero points; it is not a completed swim.

The app **does count** the row for the entry cap. `countSwimmerEntries` scans matching event rows and filters only configured time trials and exhibitions (`packages/core/src/lib/swimmerEntryLimits.ts:122-160`); it does not filter DQ/DFS/NS or inspect time validity. A plain DFS row like Gotaas's therefore consumes one distinct individual event entry, with prelims/finals deduplicated by event key. This matches an entry cap if the cap means events the swimmer was entered in, including a declared false start on race day; the available code/docs establish the product's entry-count policy, but do not establish a separate NSISC rule that expressly excludes DFS. Recommendation: retain this counting behavior unless a primary NSISC rule source says the cap counts only completed swims. Do not equate “non-scoring” with “not entered.”
