# Backend logic audit — 2026-10-02

Scope: `backend/{parse_meet,pdf_parser,point_calculator,psych_parser,team_rankings_parser}.py`, `apps/shell/lib/**`, `packages/db/src/**`, with scoring comparison to `packages/core/src/lib/utils.ts`. Repository instructions and vault notes `01-Architecture-Overview.md`, `02-Invariants-and-Gotchas.md`, and `06-Data-Provenance-Rules.md` were read. No application or tests were run; findings below are inferred from source.

Ranked by likelihood and impact of silently producing plausible wrong results.

## Findings

1. **A rankings extraction error silently removes the meet event cutoff.** `backend/parse_meet.py:65-83` catches every exception from the optional official team rankings parser and returns `None`; `main()` then passes `None` as `scored_event_number_max` (`:100-104`). The scorer documents that `None` means every event scores (`backend/point_calculator.py:214-215`, `:307-320`). Concrete input: a meet PDF whose athlete extraction succeeds and includes Event 43, with rankings reporting “Through Event 42” but its team-score block triggers a parse exception. Wrong output: Event 43 rows are included in calculated totals because the cutoff is discarded. **Inferred.**

2. **Missing or malformed result values become plausible zero/men values at the API mapping boundary.** `apps/shell/lib/routes/parsingPipeline.ts:99-115, 133-147` maps an absent/unparseable rank to `0`, a nonnumeric calculated point value to `0`, and every gender other than exact `Women` to `Men`; it also stringifies missing athlete/team/event fields (`:107-115`). Concrete input: `rank: "DQ"`, `calculated_points: "bad"`, missing gender. Wrong output: the stored row becomes rank 0, 0 points, and Men instead of preserving an absent rank, surfacing invalid points, and retaining unknown gender. This can make a row look like an ordinary unplaced men’s result. **Inferred.**

3. **Scoring preset write paths accept IDs without applying the ID validator before constructing paths.** `apps/shell/lib/routes/scoringPresetRoutes.ts:179-180` joins the raw ID into a filename; the create/update handlers use that helper at `:325-333` and `:351-356`. Delete validates with `USER_PRESET_ID_RE` (`:378-381`), but write does not visibly do so. Concrete input: an ID such as `../../outside` can resolve outside the presets directory (subject to route/body schema acceptance); wrong output: write can target an unintended JSON path. **Inferred;** confirm `parsePresetWrite`’s schema acceptance before treating exploitability as established. The loader sanitizes IDs separately (`:183-187`), so read/write behavior also differs.

4. **Timestamp-only temporary PDF names collide for concurrent requests.** `apps/shell/lib/routes/parsingRoutes.ts:46-48, 60-61` and `:74-76, 104-105` use `Date.now()` as the entire unique component, synchronously overwrite that path, then each request unlinks it. Concrete input: two PDF uploads reach one endpoint within the same millisecond. Wrong output: one parser can read the other request’s bytes, or one request can delete the file while the other parser is using it. **Inferred.**

5. **Python scoring has a silent D2 default when settings are absent.** `backend/point_calculator.py:9, 213-224` defaults to `DEFAULT_NCAA_D2_SCORING` and relay multiplier 2 when no scoring configuration is found. The architecture note identifies the TypeScript `calculatePoints` in `packages/core/src/lib/utils.ts` as the product scoring engine (vault `01-Architecture-Overview.md`; repo `packages/core/src/lib/scoringEngine.ts:117`). Concrete input: invoke the Python scorer for a meet in another division without a settings file. Wrong output: D2 place points are emitted rather than requiring settings or preserving unknown scoring. **Inferred.**

6. **Python and TypeScript PDF-place scoring differ on malformed point strings.** Python `backend/point_calculator.py:124-129` accepts values coercible by `float`, including whitespace-wrapped numeric strings, and converts invalid/missing values to zero; TypeScript `packages/core/src/lib/utils.ts:2344-2350` accepts only a finite numeric `pdfPoints`. At the HTTP bridge, `apps/shell/lib/routes/parsingPipeline.ts:126` applies `Number(a.pdf_points)`. Concrete input: raw `pdf_points: ""` becomes Python 0 and bridge TypeScript 0; `"12pts"` becomes Python 0 and TypeScript `NaN` (ultimately rejected by `Number.isFinite`). The final credited value is zero in both, but malformed input is silently normalized rather than rejected; this is a provenance/diagnostic defect, not a demonstrated numeric parity difference.

7. **JSON backup writes are not atomic.** `apps/shell/lib/workspaceRepo.ts:80-92` writes the complete backup directly to its final `.json` path. Concrete input: process termination or disk failure during `writeFile` leaves a truncated file listed as a backup. Wrong output: a later restore sees an existing but invalid/incomplete backup. **Inferred.**

## Scoring parity review

The Python and TypeScript PDF-place branches use the same visible ordering for exhibition, outside-scored-program boundary, time trials, and nonnegative finite printed points (`backend/point_calculator.py:114-130`; `packages/core/src/lib/utils.ts:2344-2350`). The Python conversion and bridge coercion can conceal malformed source types, as finding 6 describes.

The Python regular scorer implements ties, relay multiplier, time-trial/championship handling, and scorer caps in a separate implementation (`backend/point_calculator.py:257-320, 1084-1150+`). The TypeScript engine has substantially richer explicit tie-group and dead-heat logic (`packages/core/src/lib/utils.ts:1467-1547, 1607-1663, 2373-2424`). I did not execute a differential corpus, so I cannot claim a specific numeric mismatch in those branches. The proven structural risk is duplicated logic plus the D2 fallback in finding 5.

No confirmed SQL injection was found in the reviewed database sources: queries use prepared statements and bound values (for example `packages/db/src/WorkspaceService.ts` and `PgWorkspaceService.ts`). Backup restore paths are routed through basename/allowlist checks in the workspace routes/repositories; no confirmed traversal was identified there. Error responses in the inspected parse routes use 4xx/5xx for failures; no confirmed error-as-200 path was established.
